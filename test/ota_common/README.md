# OTA download test bench

The OTA download core (`lib/OTA/src/ResumableDownloader.*`) is transport-agnostic, so it runs on the host.
Two suites cover it, both in the shared `native` PlatformIO environment:

- `test/test_ota_download` — Unity tests against a scripted in-memory fake server. Deterministic coverage of
  redirects, drops, stalls, 5xx, `Range`/`If-Range` resumes, asset swaps, ignored ranges, 416, bad
  `Content-Range`, retry budget and backoff, sink failures.
- `test/test_ota_loadtest` — the same core over real POSIX sockets against `chaos_server.py`, a GitHub
  release-asset emulator with seeded fault injection (drops, stalls, 503, stripped `Range`, throttling,
  token expiry). Downloads assets up to 4 MiB many times and checks every byte. Skipped unless
  `OTA_CHAOS_URL` is set.

Run everything locally:

```shell
scripts/ota_testbench.sh              # starts the chaos server, runs both suites
OTA_LOAD_ITERATIONS=200 scripts/ota_testbench.sh   # longer soak
pio test -e native -f test_ota_download            # unit suite only, no server needed
```

The asset bytes are generated by the same xorshift32 stream in `asset_gen.h` and `chaos_server.py`, so the
test can verify a download without transferring a reference copy. CI runs the bench in
`.github/workflows/ota-testbench.yml`; the release and nightly builds depend on it.

Not covered on the host: the `esp_http_client` adapter (`EspHttpTransport`), TLS, and the `esp_ota_*` sink.
Those stay thin on purpose and need an on-device check before a release.
